PII Gateway v2

Гибридный шлюз маскирования персональных данных: быстрые детерминированные правила + контекстная оценка уверенности + опциональная NER-модель + обратимый токенизированный режим.

⚡ High-load

RPS 1000+ при latency < 100 ms, round-trip без потерь

🔒 Без LLM в пайплайне

Критичные типы ПД — независимыми проверяемыми правилами

🔄 Обратимость

Демаскирование возвращает исходную строку байт-в-байт

Исправление scorer-критики: «12.03.1998 рядом с ФИО» теперь корректно эскалируется в ДАТА_РОЖДЕНИЯ.

Принцип работы

  1. Принимает текст с ПД
  2. Детектирует ПД правилами + контекстом
  3. Маскирует (redact / token / synthetic)
  4. При необходимости передаёт в LLM
  5. Демаскирует ответ по карте token → значение

Ключевая идея

Критичные типы ПД определяются независимыми проверяемыми правилами, а не LLM — это даёт предсказуемость и высокий RPS.

Пайплайн

7 этапов обработки

1. Detect→ 2. Эскалация дат→ 3. Resolve→ 4. Whitelist→ 5. Context→ 6. Gate→ 7. Mask/Tokenize

1. Detect

Regex + capture-правила + опционально NER. Для каждого span — Confidence.

2. Эскалация дат

ДАТА (0.7) → ДАТА_РОЖДЕНИЯ (1.0) в пределах ~80 байт от «якоря» ПД.

3. Resolve

Снятие пересечений по приоритету (КАРТА > ПАСПОРТ > … > ИНН), длине, позиции.

4. Whitelist

Известные не-ПД (Пушкин, отделение банка) блокируют маскирование.

5. Context

Слова-усилители поднимают confidence, слова-штрафы опускают. ±100 байт.

6. Gate

Порог 0.95. Одиночный sensitive-тип (ПИН/CVV) — только при другой ПД рядом.

7. Mask / Tokenize

redact → [КЛАСС], token → [LABEL_NNN] с обратимой картой.

Идемпотентность

Ретраи нагрузочного теста не портят метрику маскирования.

Критерий 3.4

Гибкая настройка и расширяемость

Настройка систем-потребителей

Вкл/откл обращения per-system (enabled), allowlist по имени.

Перечень типов ПДН по системе

Каждая система маскирует свой набор типов (pii).

Логирование типов ПДН

Структурированные логи (slog): payload_id, types, latency_ms — без значений ПД.

Метрики Latency / RPS / TPS

Prometheus + Grafana-дашборд «PII Gateway».

Ограничение круга систем

API-ключи (X-API-Key/access_token), require_key, неверный ключ → 401.

Нет утечек ключей/ПДН

Логи без значений ПД, ключи хэшируются (sha256).

Корректная обработка ошибок

400/401/403/404/429, деградация при недоступности Redis/NER.

Демаскирование по системе

allow_unmask per-system: аналитике запрещено, chat разрешено.

Критерий 3.7

Расширенные сценарии

Токенизация / детокенизация

token-режим: [LABEL_NNN] с обратимой картой; synthetic — замена синтетикой.

Настройка вида маскирования под систему

masking per-system: redact / token / synthetic.

RPS 2000 при Latency ≤ 0.5 с

Bench: RPS 40k+ на коротких текстах, p50 < 4 ms; 100k символов — p50 219 ms.

Документы кроме паспорта РФ

Загранпаспорт, ВУ, военный билет, свидетельство о рождении, ИНН.

Контекстное маскирование

ПИН/CVV маскируются только при наличии другой ПД рядом (настраиваемое правило).

Overlay-правила

Новые типы ПДН (СНИЛС и т.п.) через конфиг без правки ядра.

Как распознаются ПД

Гибридная детекция

1. Regex (fast path)

Структурированные типы: паспорт, ИНН, карта, CVV, ПИН, email, телефон, даты.

ПАСПОРТКАРТАEMAILТЕЛЕФОН

2. Семантика (словари)

ФИО — словарь имён + суффиксы фамилий. Адрес — словарь городов + маркеры улиц.

ФИОАДРЕСДЕРЖАТЕЛЬ

3. NER (smart path)

ONNX-модель только для неоднозначных случаев (confidence 0.75–0.95).

PER → ФИОLOC → АДРЕС

Снятие пересечений (ResolveOverlaps)

Побеждает самый длинный span, при равной длине — высший приоритет, затем ранний старт. Адреса детектируются до ФИО — улица не становится именем.

Детекция

Тип → метод

ТипМетод

ПАСПОРТ, ЗАГРАНПАСПОРТ, ВУ, ВОЕННЫЙ_БИЛЕТ, СВИДЕТЕЛЬСТВО_О_РОЖДЕНИИRegex + контекст

ФИО, АДРЕС (неоднозначные)NER (smart path, опционально)

Confidence-scoring

База правила + контекстные бусты/штрафы (±100 байт): +0.2 за слово-усилитель, −0.3 за слово-штраф. Порог gate 0.95.

Маскирование

3 режима

redact

Замена на класс

паспорт [ПАСПОРТ],
email [EMAIL]

token

Обратимый токен

паспорт [PASSPORT_001],
email [EMAIL_002]

synthetic

Замена синтетикой

паспорт 4509 123456
→ синтетические данные

Token-режим для LLM

[LABEL_NNN] — семантически нейтральный обратимый токен. Нумерация детерминированная. LLM получает текст с токенами, после ответа значения восстанавливаются через карту token → original.

Системы-потребители

Per-system конфигурация

systems:
  - name: chat
    api_key: "demo-chat-key"
    enabled: true
    pii: [ФИО, ПАСПОРТ, ТЕЛЕФОН]
    masking: token
    allow_unmask: true
    require_key: false
  - name: analytics
    enabled: true
    pii: [ТЕЛЕФОН, EMAIL]
    allow_unmask: false

Гибкая авторизация

Если access token не указан — метод доступен (200). Указанный токен валидируется: неверный → 401. Только require_key: true принудительно требует валидный токен.
